# `depends_on` 的语义缺口：7 个服务提出 29 条待补依赖，但没人定义这个字段管什么

日期：2026-11-06　范围：`contracts/service-catalog.v2.json`　状态：**待裁决，未改任何值**

## 0. 一句话

七份方案各自说「`depends_on` 缺 X」，合计 **29 条**（原写 30，见 §8）。但 `depends_on` 在仓库里**没有语义定义**——
它既可能是"同步调用依赖"，也可能是"事件消费依赖"，也可能兼有。在这条定下来之前，
补任何一条都是猜口径。**本文不给值，只把这 29 条和它们的口径分歧摆出来。**

## 1. 已核实的现状

- `depends_on` 的全库定义：**零处**。`docs/01`–`17`、`contracts/*.md`、`README.md`、`AGENTS.md`
  里都搜不到这个词的解释。
- 它有两个消费者。`tools/scaffold/generate_services.py` 第 104–106 行把数组原样写进
  `services/<slug>/service.yaml` 的 `depends_on:` 列表，不做校验、不做推断；
  `tools/check_all.py` 的 `check_catalog`（第 294–314 行）会校验它——查重复目标、非字符串项、
  自环、未知 `service_id`，但**明确不查可达性与环**。这份报告写成于 2026-11-06 04:20
  （`dac6705`），第二个消费者是同日 14:50 的 `ee0d2c3` 加上去的，见 §8 第 5 条。
- 因此 `depends_on` 目前只是**一个字符串数组**，不是契约。

## 4. 加进去会撞到的两件事

### 4.1 已有的 S26 ⇄ S27 环

`S26.depends_on = [S25, S22, S23, S27]`，`S27.depends_on = [S26]`——双向。
[S27 §9](../../plans/S27-provider-connectors.md) 明确这是**有意设计**：两条 Kafka 边异步、
唯一同步边 `:claim` 方向 S27→S26，"没有反向同步依赖"。

但如果按 S39 的口径把事件依赖也写进 `depends_on`，这个环会被当成真实环；
按 S13 的口径，`S26 → S27` 这条（S26 发 `connector.submit.requested` 给 S27）也不该进 catalog。
**两种口径下 S26 ⇄ S27 都有问题，只是问题不同。**

### 4.2 加上 S41 / S43 的边是**倒分层**（但不形成新环）

S32/S33/S34 要加 S41（时间线），S34 还要加 S43（交付）。`S41.depends_on` 是
`[S08, S28, S19]`，`S43.depends_on` 是 `[S08, S28, S35, S36, S37]`，两组里都**没有**
生产组（S29–S34）或 S39 的服务。反向也成立：在 catalog 现图上，从 S41 出发、
从 S43 出发能到达的生产组服务都是 **0 个**（`closure(S41)`、`closure(S43)` 与
{S29,S30,S31,S32,S33,S34} 的交集为空）。

因此把 S32→S41、S33→S41、S34→S41、S34→S43 这四条边加进去**不会产生新环**——
全 29 行（32 条边）都加上之后，图上仍然只有 `S26 -> S27 -> S26` 这一个环，
而它在基线就已存在（`S26.depends_on` 含 `S27`，`S27.depends_on = [S26]`），
与 S41/S43 无关。

真正的问题是**分层**，不是环：这会让生产组声明依赖 post 组，而 §5 第 3 问
（生产组是否该依赖 post 组）没定下来之前，这条边的方向就是待裁决的。
原写「会形成新的跨域环」「部署顺序会变成不可排序」，见 §8 第 4 条。

```bash
python -I -c "
import json, io
```

`io.open(..., encoding='utf-8')` 不能省：Windows 上 `json.load(open(path))` 按 GBK 解码，
这份 catalog 里有非 ASCII 字节，会直接 `UnicodeDecodeError` 而不是读出数据。
本报告第一版贴的就是不带 encoding 的那行，**在任何 Windows 机器上跑都是报错，不是结果**。
